## What changed

The bidi gate no longer scores a bare ASCII numeral as a Latin run, so a plain
Persian sentence like `حداکثر 253. مقدار` is clean instead of being reported
broken as `"253. "`. A run still counts as Latin the moment an `[A-Za-z]`
letter sits in it, so `VLESS://` and `IP 253. ` are caught exactly as before.
The gate also names the key when a `fa.json` value is not a string, instead of
only throwing `value.match is not a function`.

## Files

- `src/meta/bidi.test.js` — new `LETTER = /[A-Za-z]/`; `latinRuns` filters out
  runs with no letter in them; a seventh `WORKED_EXAMPLES` row for the numeral
  case with its measured verdict and a rewritten header saying which rows are
  doc measurements and which is a gate measurement; a new
  `does not read a bare Persian numeral as a Latin run` case; a non-string-value
  assertion inside `found the file it audits`.

Nothing else changed. `src/i18n/locales/fa.json` was mutated as reverted proof
scaffolding only (see *Scaffolding removed*).

### Verification

*A Persian sentence whose only Latin-class characters are digits is not reported
broken.* — Confirmed by the live-gate run above: with
`حداکثر 253. مقدار` sitting in `fa.json` as a real value, the gate's
`no value ends a Latin run on punctuation` report contains only the
`VLESS://` key. Also confirmed at helper level for the plan's edge case:
`brokenRuns('بین 8-12 عدد')` is `[]`, as it was before the change — `8-12` was
already clean because its trailing neutral is one space, and it is clean after
for the stronger reason that it is not a Latin run at all.

Note on the shape of the fix: the filter is applied to the *finished* run, not
to the character class, so a digit that shares a run with a letter is still
Latin. `IP 253. ` stays broken, which matches the bidi algorithm giving a number
the direction of the strong character in front of it. Removing `0-9` from
`LATIN` outright would have been wrong — it would have split `VLESS:// 253 و`
into a run ending on `:// ` and reported a break that does not exist.

### The `controlsIn` TypeError handed over by R3

**Decision: added the guard here, in this file, and kept it small.**
`found the file it audits` now also asserts that no `fa.json` value is a
non-string, listing the offending keys. Measured with `"scaffold.numeric": 253`
added to `fa.json`:

```
 × src/meta/bidi.test.js > fa.json is free of invisible bidi fixes > found the file it audits
   → non-string values in fa.json — this gate reads every value as text: expected [ 'scaffold.numeric' ] to deeply equal []
 × src/meta/bidi.test.js > fa.json is free of invisible bidi fixes > no value carries a bidi control character
   → value.match is not a function
```

Why not rely on `locales.test.js`: this gate is run alone often enough (it is
the fast one, and it is the one an author editing `fa.json` reaches for), and a
fa-only fault reaching it produced a message that named neither the key nor the
file. Two gates apart is too far for a two-second answer.

Why the guard does not *stop* the `TypeError`: it deliberately does not filter
the bad value out of `entries`. Filtering would make the value silently skip
both bidi checks, which trades a loud bad message for a quiet blind spot.
The `TypeError` still fires on the next test, but now a named assertion sits
directly above it saying which key caused it. That is the whole ask; anything
more is a second implementation of `locales.test.js` inside this file.

## Production pass

1. Failure paths: the only failure path this file has is `readFileSync` /
   `JSON.parse` at module load, unchanged, and it fails the whole gate loudly —
   which is the correct behaviour for a gate. The one path this unit *added* is
   a non-string value, and it now goes somewhere with the key named (above).
2. Untrusted input: `fa.json` is the input, it is in-repo and reviewed, and the
   new assertion is exactly the boundary check for it — a value that is not text
   is rejected with the key in the message rather than assumed well-formed.
3-8. n/a — a vitest file of pure string functions reading one repo file at
   module load: no secrets, no logs, no connections or timers, no remote call,
   no retry, no migration, nothing to roll back beyond `git revert`. Size is 53
   `fa.json` keys against a linear scan; the added `.filter` is one pass over
   runs already in memory, so the gate stayed at 15ms.
9. Public surface: `latinRuns` and `LETTER` are module-private to this test file
   and nothing imports it — `src/meta/` gates import nothing and are imported by
   nothing. The change *is* a behaviour change to the gate's verdict, and that
   is the point of the unit; it is stated in the commit subject.

## Notes for the next unit

- For **R9** (browser measurement) and **R10** (`docs/agents/persian-style.md`):
  the gate judges *shape*, never rendering, and after this unit its rule is
  precisely "a run containing at least one `[A-Za-z]` must not end on two or
  more neutral characters". Digits are passengers, not drivers. If R10 writes
  the gate's scope into the doc, that is the sentence to write — the doc's
  current "A Latin run must end on a Latin letter" reads as if `253.` were in
  scope, and it now is not.
- The doc's `## Digits` section (`443`, `80`, `8-12`, `2 لینک`) and its `## RTL`
  rule 2 were in quiet conflict before this unit: the first mandates ASCII
  digits, the second as-enforced punished the most ordinary way to write one.
  R10 may want to say so explicitly rather than leaving the next author to
  rediscover it.
- The seventh `WORKED_EXAMPLES` row is flagged in the file's own comment as a
  gate verdict, not a doc verdict. If R9 measures `حداکثر 253. مقدار` in a real
  browser, that row's `why` can be upgraded to a rendering measurement — and if
  the browser disagrees with the gate, this unit's premise is the thing to
  re-examine, not the row.
- `src/meta/bidi.test.js` is CRLF, like the rest of the repo. Scripted patches
  need CRLF-aware anchors or they silently find nothing.
