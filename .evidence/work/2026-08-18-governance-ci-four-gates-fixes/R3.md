# R3 — Close the locale gate's three holes

status: done

## What changed

The locale gate now rejects three inputs it used to accept in silence: a key
`src/` renders that no locale file defines (it rendered on screen as the raw
key), a locale value that is empty, whitespace-padded or nested rather than a
usable string, and a dead key under the `theme.` prefix. The `theme.` prefix is
no longer a blanket exemption — the gate composes the live key set from the
three names in `src/theme/index.js`, so `theme.auto` is an orphan the day it is
added. Fixing the nested-value hole also removes a bare `TypeError` that the
bidi gate used to throw instead of a message.

## Files

- `src/meta/locales.test.js` — new `unknownKeys` (reverse orphan check, namespace
  set derived from `en.json`), new `valueFault`/`valueFaults` (every value must
  be a non-empty trimmed string), `themeNamesIn` + `composedThemeKeys` replacing
  `EXPECTED_DYNAMIC_PREFIXES` as the exemption mechanism, `orphans` reduced to
  `keys` vs a composed `live` list, and the canary extended to assert theme
  names were actually read.

## Evidence

The gate reads the real repository from disk, so the only way to feed it a bad
input is to put one there. Each hole below was made real in the live tree, the
gate was run against it, and the mutation was reverted. Focused command in every
case: `npx vitest run src/meta/locales.test.js` (14 tests, all green before each
mutation).

### Acceptance criteria

- [x] **Each of the three holes has a fixture that fails before its fix and
  passes after, with both runs recorded.** — satisfied in the stronger mutation
  form described under "Interruption": each hole was made real in the live tree
  and the *real* gate observed going red naming the offending key, then reverted
  and observed green. Each hole additionally carries a permanent in-file fixture
  that needs no scaffolding: `names a key the source renders and no locale file
  defines` (`locales.test.js:216`), `names an empty, padded or nested value`
  (`:165`), and `reports a key under a composed prefix that no theme composes`
  (`:188`).
- [x] **The namespace set and the theme set are both derived, not hard-coded.**
  — checked by reading the file, not by trusting the diff summary.
  - namespace set, `locales.test.js:106`:
    `const namespaces = new Set(keys.map((key) => key.split('.')[0]))`, where
    `keys` at the single real call site (`:211`) is `locales.en` — the top-level
    keys of `en.json` itself. No `(app|input|rows|…)` literal exists anywhere in
    the file.
  - theme set, `locales.test.js:138`:
    `const themeNames = themeNamesIn(read(themeModule))` with `themeModule =
    join(root, 'src', 'theme', 'index.js')` (`:17`), and `themeNamesIn` (`:40`)
    matching `/const themes\s*=\s*\[([^\]]*)\]/` then the quoted names inside.
    `composedThemeKeys` (`:50`) maps those to `theme.<name>`. The canary at
    `:148` fails if that read ever yields nothing, so a renamed module or a
    reshaped literal turns the suite red rather than silently exempting nothing.
  - two further exclusion sets in `unknownKeys` are derived rather than listed,
    which the criterion did not require: `prefixes` from the source's own
    composed-call sites, and `fileNames` from `basename` over the walked file
    list (so a comment mentioning `rows.js` is not read as a key).
  - **the one remaining literal, stated plainly.** `locales.test.js:176`:
    `expect(prefixes.sort(), …).toEqual(['theme.'])`. This is the pin the plan
    intended to keep, not a leftover. The plan's item 3 targets the blanket
    *exemption* — `EXPECTED_DYNAMIC_PREFIXES` fed into `orphans`, which let any
    `theme.*` key pass forever — and that is gone: `orphans` no longer takes a
    prefix list at all. What `:176` pins is the *inventory* of composed-call
    sites, and it fails closed: a new `t(prefix + x)` anywhere in `src/` turns
    the suite red and the message says to compose its live key set the way
    `theme.` is. Deriving it would defeat the point, since the whole job of the
    assertion is to notice that the derived set changed.

## Production pass

- 1 — every failure path goes somewhere: the two new file reads are the same
  unguarded `readFileSync`/`JSON.parse` the gate already used. A missing or
  malformed `src/theme/index.js` throws at import and the suite goes red, which
  is the correct outcome for a gate: it must not degrade into passing. A
  *renamed* module would throw rather than silently exempt nothing, and the
  `themeNames.length > 0` canary at `:148` covers the case where the file exists
  but the literal was reshaped.
- 2 — untrusted input at the boundary: the inputs are this repository's own
  files, read by a test that only ever runs in CI and locally. The regex-based
  reads (`themeNamesIn`, `dynamicPrefixes`, `quotedStrings`) are lenient by
  design — they cannot throw on unexpected shapes, they return nothing, and the
  canary turns *that* into a red.
- 3, 4, 5, 7, 8 — n/a: a test file with no secrets, no long-lived resources
  (`readFileSync` only), no remote call, no runtime deployment and nothing to
  roll back. It is reverted by reverting the commit.
- 6 — behaves at real size: `unknownKeys` and `orphans` are `Array.includes`
  inside a filter, so O(quoted × keys) — currently a few thousand quoted strings
  × 53 keys, running in single-digit milliseconds inside a 14-test file that
  completes in well under a second. It stays comfortable to an order of
  magnitude more keys; a `Set` swap is the fix if it ever stops being.
- 9 — the public surface is honest: this is a repo gate, and the honest
  statement is that it got **stricter** in three ways. Any branch carrying a key
  rendered but undefined, an empty/padded/nested locale value, or a dead
  `theme.*` key will now fail CI where it previously merged. None exist on
  `master` today (verified: 0 faults across all four files, 14/14 green), so no
  existing work is broken by this.

## Notes for the next unit

- **R4 (`src/meta/bidi.test.js`) — the finding from hole 2, and it is R4's.**
  `controlsIn` at `bidi.test.js:101` calls `value.match(...)` with no type check,
  and `:130` maps it over every `fa.json` entry. A non-string value there throws
  `TypeError: value.match is not a function` with no key name and no indication
  which file or key is at fault. R3's `every value is a usable string` now
  catches the nested value *first* in a different file, so in practice the
  locale gate reports it with the key named — but that is two gates apart, and
  `bidi.test.js` still crashes rather than reports if it is ever run alone or if
  a fa-only fault reaches it. R4 may want a guard or an explicit
  "every value is a string" assertion ahead of `:130`; if it decides the locale
  gate is sufficient upstream cover, that is a defensible call worth stating
  rather than leaving implicit.
- **`bidi.test.js` reads `fa.json` only** (`:29`). Any mutation proof R4 takes
  must be in `fa.json`; editing `en.json` leaves the bidi gate green. The plan
  text for R3 did not mention this and it cost a run to discover.
- **Mutation proofs against `src/meta/` gates need the real files.** These gates
  read from disk and cannot be fed a fixture through an argument. The pattern
  that worked here: copy the target to the scratchpad, mutate in place, run
  `rtk proxy npx vitest run --reporter=verbose <file>` for the full assertion
  diff, restore from the copy, then confirm with `git status --porcelain`.
- **The default (json) reporter truncates arrays** in failure messages —
  `expected [ Array(2) ] to deeply equal []` with no contents. Use
  `rtk proxy npx vitest run --reporter=verbose` when the evidence needs the
  actual values.

  learned here bears on it; R3 touched no `src/utils/` file and no locale key
