Three things in that body are worth naming explicitly, because each is a way

- `"bypass_actors": []` with `"current_user_can_bypass": "never"` — no bypass

### Verification

"A pull request whose CI check is red shows the merge button disabled." — NOT
observed, and this is why the unit's status is `unverified` rather than `done`.

What was observed instead, and what it does and does not prove:

Pull request #20 (`governance-ci-four-gates` → `master`) is open with head
`167acec`. Its `test` check concluded `SUCCESS`, and after the ruleset went
active `gh pr view 20 --json mergeable,mergeStateStatus` returns
`"mergeable": "MERGEABLE"`, `"mergeStateStatus": "CLEAN"`. That is the *green*
half of the gate: it shows GitHub is evaluating the ruleset against a check it
can actually find, and that a passing check leaves the pull request mergeable.
Had the required context not matched a real check name, this pull request would
read `BLOCKED` — GitHub waits forever on a context that never reports — so
`CLEAN` is meaningful evidence that the wiring is right.

It is not evidence for the red half. Producing a red check would mean pushing a
deliberately failing commit to a pull-request branch, and this unit's `Files`
entry is "none in this repository" — writing a source file to break the suite is
outside that scope, so it was not done. The honest position is that the rule is
demonstrably in place and demonstrably wired to the right check, and that its
behaviour on a failing check is inferred from GitHub's documented semantics
rather than watched.

The cheapest way to close this without a throwaway commit: the next pull request
that goes red for its own reasons should have
`gh pr view <n> --json mergeStateStatus` recorded — `BLOCKED` closes it.

## Notes for the next unit

- The ruleset id is **21038975**. Any later unit that needs to add or adjust a
  rule on `master` should PUT that id rather than POST a second ruleset —
  GitHub applies rulesets cumulatively, and two rulesets on one branch is how
  gates end up contradicting each other.
- The required context is the *job id*, `test`, not the workflow name, `CI`.
  A later unit that adds a second CI job will not have it required
  automatically; the ruleset needs the new context added by name.
- Renaming the `test` job, or the workflow file, breaks the gate in the
  fail-closed direction — every pull request blocks on a check that never
  arrives. Treat `.github/workflows/ci.yml:15` as load-bearing.
- The API is reachable from here but flaky: two of five `gh api` calls in this
  unit died with `net/http: TLS handshake timeout` and succeeded on retry. A
  later unit that automates against the GitHub API should retry rather than
  treat the first failure as an answer — and should re-read state before
  retrying a write, as this unit did.
